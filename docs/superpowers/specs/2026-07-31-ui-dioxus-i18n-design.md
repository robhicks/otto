# Dioxus UI localization design

> **Status:** IMPLEMENTED — shipped in [#118](https://github.com/robhicks/otto/pull/118).
> An i18n layer for `ui-dioxus/` with `en`/`de`/`es`/`hi`/`zh-Hans` catalogs,
> environment detection, a persisted in-UI language picker, and a live locale switch.
> **Implements:** [#114](https://github.com/robhicks/otto/issues/114).
> **Depends on:** the Dioxus migration (COMPLETE) — `docs/superpowers/plans/2026-07-22-ui-dioxus-migration.md`.

`ui-dioxus/` has no localization today: every user-facing string is an inline English literal in
the RSX, in `net/view_model.rs`, or in `editor/mod.rs`. This spec picks the mechanism, draws the
translate-vs-leave-alone boundary explicitly, and specifies the picker + the crate's first
persistence layer.

---

## Premise corrections

Three of the issue's premises do not survive contact with the repository. They are corrected here;
the issue is otherwise accurate.

1. **The string inventory is incomplete.** The issue enumerates the components, `view_model.rs`,
   `app.rs`, and `desktop_boot.rs`. It omits **`src/editor/mod.rs`**, which carries three
   user-facing strings — `"No file open"` (`editor/mod.rs:66`), `"binary file — not editable"`
   (`:69`), and `"file too large to edit"` (`:70`) — and **one string in `app.rs`** that is not in
   the listed cluster: the client error `"URL and token are required"` (`app.rs:78`). It also omits
   `view_model.rs`'s diff markers `"(trailing newline added)"` / `"(trailing newline removed)"`
   (`view_model.rs:94-96`). All six are in scope; the AC's "no user-facing string literal remains"
   cannot be met without them.

   It further omits a **cluster that is deliberately left untranslated**: the crate-authored
   *diagnostics* in `transport/web.rs`, `transport/desktop.rs`, and `desktop_boot.rs` — four
   distinct messages across seven sites. `"socket closed"` (`transport/desktop.rs:23`);
   `"workspace rpc failed: HTTP {status}"` (`transport/web.rs:82,102`,
   `transport/desktop.rs:104,124`); `"unexpected response to List"` (`transport/web.rs:82`) and
   `"unexpected response to Read"` (`transport/web.rs:113`, `transport/desktop.rs:135`); and
   `"failed to launch \`{bin} serve\` sidecar: {e}"` (`desktop_boot.rs:147`). §2 draws the line
   that excludes them and says why.

2. **"A test that fails when a key is missing from any locale" understates what is achievable.**
   The issue's AC asks for a runtime completeness test. With the mechanism chosen in §1, a missing
   key is a **compile error**, not a test failure — the catalog is one exhaustive `match` with no
   wildcard arm. The runtime test still ships (§7) because it catches a *different* failure, an
   empty-string stub, which the compiler cannot. This over-satisfies the AC rather than replacing it.

3. **The event log cannot be localized by string extraction alone.** `LogRow.text` is a
   pre-formatted `String` pushed into a `Vec` at event-arrival time (`app.rs:156`). Extracting the
   literals inside `describe_event` would localize a row *at the moment it is created* and then
   freeze it — a locale switch would leave every already-received row in the old language, in the
   surface where most of the UI's text lives. Meeting the issue's "switching re-renders the UI
   immediately" requires deferring formatting to render time, which is a structural change to
   `LogRow`, not a literal extraction. **See §6.**

## Scope

**In:** an i18n module in `ui-dioxus/src/i18n/`; extraction of every in-scope literal (§2) from the
RSX, `view_model.rs`, `editor/mod.rs`, `app.rs`, and `desktop_boot.rs`; five catalogs; locale
detection on both targets; a persisted language picker; the `LogRow` deferred-formatting refactor
(§6); doc updates so new components don't regress the rule.

**Out:** the engine and `otto serve` CLI output (explicitly, per the issue); server-originated text
arriving over the `protocol` wire (§2); locale-aware number/date/currency formatting (§8);
right-to-left layout (none of the five locales is RTL); pluralization machinery (§8); any workspace
crate change; `index.html` `<title>` and `Dioxus.toml` `[web.app] title` (build-time single values,
not runtime copy); a general settings framework (§4 keeps persistence deliberately narrow).

`ui-dioxus/` is workspace-excluded and depends only on `otto-protocol`, so **no workspace crate is
touched and the offline-determinism suite is unaffected.** `cargo test --workspace` neither exercises
nor is exercised by this change.

## 1. Mechanism — a compile-time macro-generated catalog

### Decision

A hand-rolled, dependency-free, compile-time catalog generated by one declarative macro
(`ui-dioxus/src/i18n/catalog.rs`), rather than `rust-i18n`, the `fluent` family, or `gettext`.

```rust
messages! {
    Connect      { en: "Connect",    de: "Verbinden",   es: "Conectar",  hi: "कनेक्ट करें", zh: "连接" }
    Disconnect   { en: "Disconnect", de: "Trennen",     es: "Desconectar", hi: "…",        zh: "断开" }
    // …
}
```

The macro expands to exactly three items:

```rust
pub enum Msg { Connect, Disconnect, /* … */ }          // one variant per key
impl Msg { pub const ALL: &'static [Msg] = &[/* … */]; } // for the enumeration test (§7)
pub fn t(locale: Locale, m: Msg) -> &'static str {      // exhaustive match, NO wildcard arm
    match (locale, m) { /* 5 arms per key */ }
}
```

### Why

- **Wasm compatibility is free.** No dependency means nothing to audit for
  `wasm32-unknown-unknown`, and nothing that can regress when a transitive dep changes. `fluent`
  pulls `intl-memoizer`, `unic-langid`, `type-map`, and a runtime parser; `rust-i18n` pulls a proc
  macro plus `once_cell`-backed global state and loads YAML at build time. Both work on wasm; both
  cost bundle bytes for a ~50-key catalog.
- **The bundle budget is real and guarded.** `scripts/build-web.sh` fails the build above
  `MAX_WASM_BYTES` (1,200,000; the current optimized wasm is 795,188 B). Five catalogs of ~50 short
  strings is a few KB of `.rodata`. A Fluent runtime plus its parser is not.
- **Key completeness becomes a compile error.** Every key must supply all five locales at the macro
  call site or the invocation does not parse; `t`'s match is exhaustive over `(Locale, Msg)` with no
  `_` arm, so adding a `Locale` variant without extending the macro also fails to compile. This is
  the strongest available form of the issue's AC.
- **Translations sit side by side.** For a catalog this small, one line per key showing all five
  languages is easier to review and to keep consistent than five files that must be diffed against
  each other.

### Trade-off, stated

Adding a sixth locale means editing every entry in one file, not adding one file. For ~50 keys that
is a mechanical, compiler-enforced edit. The alternative — per-locale files plus a build-time or
test-time completeness check — trades that mechanical edit for a *weaker* guarantee (a check that
can be skipped) and a larger surface. If the catalog ever grows past a few hundred keys, revisit;
at that size, per-locale files with a generated-key check is the better shape. Recorded here so the
revisit is a deliberate decision rather than a rediscovery.

### Parameterized messages

Rust's `format!` requires a compile-time literal, so a translated template cannot be fed to it.
Parameterized messages are handled by a second entry point over the same catalog:

```rust
pub fn tf(locale: Locale, m: Msg, args: &[(&str, &str)]) -> String
```

`tf` scans the template for `{name}` placeholders and substitutes from `args`. Rules:

- An unknown placeholder (present in the template, absent from `args`) is left **verbatim** — it
  renders as the literal `{name}`, which is visibly wrong and therefore reported, rather than
  silently blanking user-facing text.
- An unused arg is ignored.
- Substitution is single-pass over the template, so a substituted **value** containing `{…}` is
  never re-scanned — a file path or a server message containing braces cannot cause a second
  substitution round. (Relevant: `{path}` and `{message}` carry attacker-influenceable content.)
- A literal brace is not escapable. No message needs one; a test asserts no catalog template
  contains an unmatched brace.

Placeholder names are part of the message contract, so `tf` is only as safe as the catalogs' being
consistent — §7 tests placeholder-set parity across locales for every key.

## 2. The boundary — what is translated and what is not

This is the decision the issue asks to be made explicitly rather than left ambiguous.

### Translated (UI copy)

| Source | Strings |
|---|---|
| `components/connection_form.rs` | `Connect`, `Connecting…`, `Disconnect`, the `token` placeholder |
| `components/prompt_bar.rs` | `Send`, `Pause`, `Resume`, `Abort` |
| `components/approval_panel.rs` | `approval needed: {path}`, `Approve`, `Reject` |
| `components/status_line.rs` | `seq {seq}` |
| `net/view_model.rs` | connection labels (`disconnected`/`connecting…`/`connected`); capability labels (`engine`/`LLM`/`sandbox`) **and** values (`local`/`remote`/`local+remote`/`offline (deterministic)`/`on`/`off`); the meter's `tok` unit; the diff markers `(trailing newline added)`/`(trailing newline removed)`; the log-row human words (§6) |
| `editor/mod.rs` | `No file open`, `binary file — not editable`, `file too large to edit` |
| `app.rs` | `Refresh files`, `Promote to remote`, `Demote to local`, `URL and token are required` |
| `desktop_boot.rs` | the folder-picker title `Choose a workspace folder` |
| new | the picker's `aria-label` |

**Capability values are translated.** The issue flags `local`/`remote`/`on`/`off` as arguably
diagnostic. They are not: they are the entire readable content of a status strip whose stated
purpose is "so lost capability is visible" (`status_line.rs:9-11`). A user who cannot read `off`
cannot see that the sandbox is off. They are UI copy and they are translated.

### Not translated — and why

| Category | Examples | Reason |
|---|---|---|
| **Server-originated text** | `EventKind::Log { message }`, `VerifyResult { detail }`, `ServerMessage::Error { message }` bodies | Produced by the engine and delivered over the `protocol` wire. The client has no key for them and inventing one would mistranslate. The **surrounding** copy (`error:`, `client:`) is translated; the payload passes through verbatim. |
| **Protocol identifiers** | `Role` names (`Planner`, `ContextFinder`, `Coder`, `Verifier`), event-kind names (`FileEdit`, `Verify`, `TurnComplete`) | Stable wire vocabulary shared with the engine, the logs, and the docs. Translating them would make a user's report untranslatable back to a maintainer. They render as-is in every locale. |
| **Crate-authored technical diagnostics** | `"socket closed"`, `"workspace rpc failed: HTTP {status}"`, `"unexpected response to List: …"`, `"failed to launch \`{bin} serve\` sidecar: {e}"` | See the boundary rule below. |
| **The URL placeholder** | `ws://127.0.0.1:8787` | An example value, byte-identical in every language. Translating a URL is meaningless. (The issue lists it; this is a deliberate divergence.) |
| **Glyphs and markers** | `▸ ✎ ✓ ✗ ● ⏸ ◷ ▾ — ↑ ↓ ·` and the dirty-buffer `●` | Not language. |
| **Structural strings** | CSS classes, file paths, numbers, session ids | Not copy. |
| **Engine/CLI output** | `otto run`, `otto serve` | Out of scope per the issue's own proposal. |

### The boundary rule

The obvious rule — *"a string the engine sent is never translated; a string this crate authored
always is"* — is **wrong**, and stating it would create a contradiction the implementer has to
resolve by guessing. `transport/{web,desktop}.rs` and `desktop_boot.rs` author four distinct
messages (across seven call sites) that are plainly this crate's, yet translating them is the wrong
call. The rule that actually holds is:

> **Interface copy — the words that describe the app's own state, its controls, and what the user
> should do — is translated. Failure diagnostics carried on the transport's `Result<_, String>`
> seam are not.**

A narrower phrasing ("actionable copy is translated") is tempting but mis-describes the table:
`No file open`, `binary file — not editable`, `disconnected`, `off`, and `seq {n}` are all purely
informational, and all correctly translated. The rule has to cover interface *state*, not only
instruction. Worked examples:

- `"URL and token are required"` (`app.rs:78`) — instruction copy. Translated.
- `"disconnected"`, `"sandbox: off"`, `"No file open"` — interface state. Translated.
- `"workspace rpc failed: HTTP 500"`, `"socket closed"` — a failure diagnostic produced on the
  transport seam. Not translated.

Three reasons this is the right line, not merely a convenient one:

1. **These diagnostics share a surface with untranslatable ones.** They land in the event log
   beside `EventKind::Log` and `ServerMessage::Error` payloads that are engine-originated and
   therefore permanently English. Translating half of a diagnostic stream produces a *more*
   confusing mixed-language log, not a less confusing one.
2. **Their audience is a bug report.** Like the protocol identifiers above, a diagnostic that
   survives translation into a maintainer's issue tracker is worth more in one language than five.
3. **Localizing them costs a seam refactor disproportionate to six strings.** `transport/mod.rs`'s
   `Sink::send`, `connect`, `list_files`, and `read_file` all return `Result<_, String>`. A
   translated diagnostic cannot be a `String` produced inside the transport — it would have to
   become a structured error carrying a `Msg` plus args, replacing the error type across both
   target implementations and every call site. That is the right change *if* the diagnostic surface
   grows; it is not proportionate today.

**Named future upgrade:** if these ever warrant localizing, the move is to replace the transport
seam's `String` error with a `ClientErr { Authored(Msg, Vec<(String,String)>), Passthrough(String) }`
— the same two-shape enum §6 already introduces for `RowMsg::ClientError`. Recorded so the path is
known rather than rediscovered.

Consequently §13's success criterion is scoped to **UI copy**, not to every literal: the excluded
categories above are enumerated exhaustively so "did the implementer miss one?" stays a checkable
question.

## 3. Locale resolution

### The `Locale` type

```rust
pub enum Locale { En, De, Es, Hi, ZhHans }
impl Locale {
    pub const ALL: [Locale; 5];
    pub fn tag(self) -> &'static str;          // "en" | "de" | "es" | "hi" | "zh-Hans"
    pub fn endonym(self) -> &'static str;      // §5 — NOT in the catalogs
    pub fn from_tag(tag: &str) -> Option<Locale>;
}
```

### `from_tag` matching

Normalize (`_` → `-`, ASCII-lowercase, trim), then:

1. Exact primary subtag: `en*` → `En`, `de*` → `De`, `es*` → `Es`, `hi*` → `Hi`.
2. Chinese is script-sensitive and must not be matched on the primary subtag alone:
   - `zh-hans`, `zh-cn`, `zh-sg`, `zh-my`, and bare `zh` → `ZhHans`.
   - `zh-hant`, `zh-tw`, `zh-hk`, `zh-mo` → **`None`** (no Traditional catalog ships; falling back
     to `en` is honest, whereas serving Simplified to a Traditional reader is not).
3. Anything else → `None`.

Bare `zh` → Simplified is a judgment call **at the level of a single tag**: Simplified is the
majority default for an unqualified `zh`, and the picker (§5) gives a reader who wants otherwise an
immediate override. But `from_tag` never sees a tag alone in production — it is called from
`resolve_locale`'s scan over an ordered list, and the composition is what decides the outcome. See
the variant-aware scan below; reasoning about `from_tag` in isolation is not sufficient.

### `resolve_locale`

```rust
pub fn resolve_locale(persisted: Option<&str>, env_tags: &[String]) -> Locale
```

Pure, browser-free, host-tested. Precedence, in order:

1. `persisted`, if it parses via `from_tag`. (An unparseable persisted value is treated as absent —
   a stale tag from a future build must not wedge the UI.)
2. The **first** `env_tags` entry that parses, subject to the Chinese-variant rule below. The list
   is ordered by user preference, so a user whose preferences are `["fr", "de"]` gets German, not
   English.
3. `Locale::En`.

**The Chinese-variant rule (the composed behavior).** Environments append the base tag after the
regional one: a browser reports `navigator.languages == ["zh-TW", "zh", "en-US", "en"]`, and POSIX
`LANGUAGE` yields `zh_TW:zh:en`. A naive "first parseable tag" scan therefore rejects `zh-TW`
(correct) and then immediately matches the bare `zh` as Simplified (wrong) — serving Simplified to
exactly the Traditional reader that `from_tag`'s rejection exists to protect, and defeating the
guarantee §3 states. Because it takes both rules to produce the bug, testing them separately
cannot find it.

The scan therefore tracks whether any `zh-*` tag has already been rejected, and if so treats a
later bare `zh` as that variant's base tag rather than an independent Simplified preference —
skipping it and continuing to the next language. `from_tag` itself is unchanged (a lone `zh` with
no other signal is still Simplified), and the suppression is narrow in both directions:

- `["zh-TW", "zh", "en-US", "en"]` → `En`; `["zh-Hant-HK", "zh", "en"]` → `En`;
  `["zh_TW", "zh", "en"]` → `En`.
- `["zh-CN", "zh", "en"]` → `ZhHans` — a genuine Simplified user matches before any rejection is
  recorded. A bare `["zh"]` alone is still `ZhHans`.
- `["zh-TW", "zh", "de"]` → `De` — only Simplified is suppressed, never an unrelated language.
- A persisted `zh-Hans` still wins over the whole scan (precedence 1 is untouched).

Environment sources, per target:

- **web:** `navigator.languages` (an ordered array) falling back to `navigator.language`. Requires
  **four** new `web-sys` features beyond the seven the crate already enables
  (`Window`/`Location`/`History`/`WebSocket`/`MessageEvent`/`CloseEvent`/`ErrorEvent`):
  `Navigator` and `Storage` (§4), plus `Document` and `Element` for the
  `document.documentElement.lang` write (§5). All four are additive and wasm-only.

  It needs **no new direct dependency**. `Navigator::languages()` returns a `js_sys::Array`, but
  `Array::iter()` and `JsValue::as_string()` are inherent methods — callable without naming
  `js_sys`, which the detection code never does. (`js-sys` is present transitively via
  `wasm-bindgen`; adding it directly would be inert.)
- **desktop:** `sys_locale::get_locales()`.
- **neither feature:** an empty slice, so `resolve_locale` yields `En`. (`cargo build
  --no-default-features` is an existing supported configuration — `editor/mod.rs:94` accommodates
  it — and must keep compiling.)

**Why `sys-locale` rather than reading `LANG`/`LC_ALL`.** The desktop target's primary launch path
is a bundled GUI app. A macOS app launched from Finder inherits none of the shell's locale env
vars, and Windows never sets them; an env-var-only detector would silently report `en` on two of
three desktop platforms — a detection feature that does not detect. `sys-locale` is a small,
dependency-light crate that queries the OS API per platform. It is added **optional, under the
`desktop` feature only**, so the wasm build neither resolves nor compiles it.

## 4. Persistence — the crate's first, deliberately narrow

Two free functions, cfg-dispatched, with no trait and no settings struct:

```rust
pub fn load_persisted_locale() -> Option<String>;
pub fn store_persisted_locale(tag: &str);
```

| Target | Store | Key / path |
|---|---|---|
| `web` | `localStorage` | key `otto.ui.locale` |
| `desktop` | a file | `<config_dir>/otto/ui-locale`, one line, the BCP-47 tag |
| neither | no-op | `None` / ignore |

Properties:

- **Best-effort, never fatal.** `localStorage` is absent or throws in some private-browsing and
  sandboxed-iframe configurations; the config dir may be unwritable. Every failure path is
  swallowed — the UI runs with detection-only behavior. A language preference is not worth an error
  surface.
- **Validated on read.** The stored string is parsed through `Locale::from_tag` by `resolve_locale`;
  garbage or a tag from a future build behaves exactly as "no stored preference." Nothing else ever
  reads this value, so a hostile `localStorage` entry can at worst select a shipped locale.
- **Written only on an explicit picker change** (§5), never on startup. Detection therefore never
  becomes sticky by accident: a user who has never touched the picker keeps following their
  environment when they change it.
- **`web-sys` needs the `Storage` feature** added alongside `Navigator` (§3).
- **Desktop writes go to the OS config dir, never the workspace root.** The UI must not create files
  inside the user's workspace: the engine indexes and edits that tree, and a settings file appearing
  there would be surprising at best. `dirs` (already a workspace dependency at `crates/engine`,
  where it is pinned `5`) resolves the config dir; it is added optional under `desktop` only, at
  version **`6`** — see risk 3 for why the two pins differ. The write is a
  single `create_dir_all` + `write` of a short ASCII tag to a fixed filename — no user-controlled
  path component, so there is no traversal surface.

This is a locale preference, not a settings framework. If a second preference ever appears, that is
the moment to introduce a real settings shape — not now.

## 5. The language picker

### Placement: `StatusLine`

`StatusLine` renders **unconditionally**, in every connection state; the capability segments and
meter inside it render only while connected (`status_line.rs:26-48`), but the strip itself is always
present. That matters: the picker must be reachable before connecting, and its most likely first use
is by someone who has just opened the app.

The alternative the issue offers — grouping it with `ConnectionForm` as a settings cluster — is
rejected: `ConnectionForm` is a connect *workflow* (URL, token, Connect/Disconnect), and placing a
display preference among fields that feed a connection implies it participates in one. It does not.

### Shape

```rust
#[component]
pub fn LanguagePicker() -> Element    // takes no props — consumes the locale from context
```

**No prop, by design.** A `locale: Signal<Locale>` prop would force `StatusLine` to grow a `locale`
prop it does not otherwise need, and `App` to thread it — for a component that is the only writer
of the signal. `LanguagePicker` consumes the context directly (via `try_consume_context`, so it is
inert rather than panicking in a provider-less mount, matching `use_locale()` below), leaving
`StatusLine`'s signature unchanged.

A native `<select>` with one `<option>` per `Locale::ALL`, `selected` on the active one, and an
`aria-label` (translated — it is the one picker string that *is* catalog copy, because a screen
reader announces it in the current language).

**Option labels are endonyms and are never translated:** `English`, `Deutsch`, `Español`, `हिन्दी`,
`中文（简体）`. They live in `Locale::endonym()`, deliberately outside the catalogs, exactly as the
issue requires — a reader stuck in a language they cannot read must still be able to find their own.

A native `<select>` is keyboard-reachable and screen-reader-labeled by default on both targets (the
desktop target is a webview), which is why it beats a custom dropdown here.

### Reactivity — no reload, no reconnect

`App` owns the locale as a `Signal<Locale>` and publishes it via `use_context_provider`. Consumers
read it through a single helper:

```rust
/// The active locale for the calling component. Falls back to `En` when no provider is in scope.
pub fn use_locale() -> Locale {
    match try_use_context::<Signal<Locale>>() {
        Some(sig) => sig(),   // TRACKED read — this is what subscribes the component
        None => Locale::En,
    }
}
```

`try_use_context` (the `dioxus-hooks` **hook**), not the bare `try_consume_context` — the hook form
caches the lookup on first render and obeys the positional-hook rules the rest of this crate already
follows. Both exist; the hook is the correct one inside a component body.

`sig()` is a **tracked read**, which is what subscribes a component to the signal, so Dioxus
re-renders exactly the subscribers when the picker writes. (This is the same tracked-read discipline
`app.rs:368-396` and `editor/mod.rs:60-63` already document; a `.peek()`/write-guard access would
not subscribe and the switch would silently not re-render.)

**The `try_consume_context` fallback is load-bearing, not defensive padding.** Plain `use_context`
**panics** when no provider is in scope, and `editor/dirty.rs`'s `render_tests::Harness`
(`dirty.rs:111-123`) mounts the real `Editor` in a bare `VirtualDom` with no provider — so the two
existing tests `clean_buffer_renders_the_path_with_no_marker` and
`dirty_buffer_renders_the_marker_after_the_path` would panic the moment `Editor` reads the locale
(which §2 requires: its three strings are in scope). Deciding this once, in a helper, means every
component — and every future provider-less SSR test — degrades to `en` instead of crashing, rather
than each component re-deciding. **No component calls `use_context::<Signal<Locale>>()` directly.**

Nothing in the connection path reads the locale: `do_connect`, `build_ws_url`, the drain task, the
sink, and the transport are all untouched. Therefore switching locale **cannot** disturb the live
WebSocket, the session, `last_seq`, the editor buffer, the dirty flag, or the log contents — the
signal write re-renders view code and nothing else. This is a structural property, not a behavior to
test for regressions, but §7 asserts it anyway at the level a host test can.

On change the picker performs exactly three things: `locale.set(next)`, `store_persisted_locale`,
and set `document.documentElement.lang` to the new tag so assistive tech announces content
correctly. The `lang` attribute is also set once at startup from the resolved locale.

The `lang` write applies on **both** real targets, not web only. The desktop target is a wry
webview with a genuine `documentElement`, so its screen reader reads the same attribute a browser
does; treating desktop as a no-op would be a `web-sys` feature-gate presented as a platform
property, and would ship a desktop user who picks 中文 a document still declaring `lang="en"`. Only
the mechanism differs — web writes the DOM directly through `web-sys` (already linked, synchronous),
desktop dispatches through `dioxus::document::eval`, which needs no `web-sys` at all. The
interpolated tag is one of five `&'static str` literals, so the script has no injection surface.
The `--no-default-features` seam-check build has no document and keeps the no-op.

`index.html`'s `<html>` element carries no `lang` today, so the pre-mount document has none until
that startup effect runs. A static `lang="en"` is added there — it costs nothing, and it means the
document is never *un*-labeled, only briefly mislabeled in the rare non-`en` case, which is
strictly better for assistive tech than an absent attribute.

### Hook-order safety

`App` gains hooks (the locale signal + its context provider, and on web the `lang`-setting effect).
Dioxus hooks are **positional**: they are added unconditionally at the top of `App`'s body, outside
any `#[cfg]` block, except the web-only `lang` effect, which sits inside the existing
`#[cfg(feature = "web")]` block — each target thus keeps its own fixed, unconditional hook sequence,
the invariant `app.rs:398-406` already states.

## 6. The event log — deferred formatting

The structural change flagged in premise 3.

### Today

`describe_event(&EventKind) -> LogRow`, where `LogRow { class: &'static str, text: String }`, is
called at event-arrival time and the formatted `String` is pushed into `rows` (`app.rs:156`,
`:160`, `:182`, `:201`, …). Formatting has already happened by the time anything renders.

### Change

`LogRow` carries **structured** data; formatting moves to render time.

```rust
/// A client-side row's payload: either authored copy (retranslates on a locale switch) or a
/// passthrough diagnostic string (§2's boundary rule — rendered verbatim in every locale).
pub enum ClientText {
    Authored(Msg),        // e.g. Msg::UrlAndTokenRequired
    Passthrough(String),  // e.g. a transport diagnostic
}

pub enum RowMsg {
    AgentStarted { role: String },        // role rendered verbatim — protocol identifier (§2)
    AgentFinished { role: String },
    FileEdit { path: String, bytes: u64 },
    Verify { ok: bool, detail: String },  // detail is server-originated — passed through (§2)
    Log { message: String },              // server-originated
    TurnComplete { ok: bool },
    ApprovalRequest { path: String },
    Meter { input: u64, output: u64 },
    ServerError { message: String },      // server-originated
    ClientError(ClientText),              // authored OR passthrough — see above
}

pub struct LogRow { pub class: &'static str, pub msg: RowMsg }
pub fn render_row(locale: Locale, msg: &RowMsg) -> String;
```

`describe_event` keeps its signature and call sites but builds a `RowMsg` instead of a `String`.
`error_row` keeps its `&str` parameter (its payload is always server-originated). `client_error_row`
takes a `ClientText`: there is **exactly one** authored call site — `app.rs:78`'s validation message
— which passes `Authored(Msg::UrlAndTokenRequired)`; the other seven (`app.rs:182,201,224,310,328,361`
and the desktop `SpawnFailed` arm at `:427`) are transport/boot diagnostics and pass
`Passthrough(…)`. `EventLog` reads the locale via `use_locale()` and calls `render_row` per row.

`RowMsg` and `ClientText` derive `Clone` and `PartialEq` so `LogRow` keeps the derives it has today
(`Signal<Vec<LogRow>>` requires them).

**`Verify`'s empty-detail case is authored copy and gets a catalog key.** Today
`view_model.rs:220-231` renders the literal `"ok"` when `detail.is_empty()`, and the server's
`detail` otherwise. `render_row` preserves exactly that branch: empty detail → `t(locale,
Msg::VerifyOk)`; non-empty → the server's string verbatim. This is the one place where a single
row is authored in one case and passthrough in the other, so it is called out rather than left to
inference.

### Why this is worth the churn

Without it, the largest text surface in the UI is localized only for rows that arrive *after* a
switch, leaving a permanently mixed-language log — which reads as a bug and would defeat the point
of the picker. Storing formatted strings is also the classic i18n mistake; this is the correction,
made once, at the only place in the crate that does it.

**Cost:** the existing `describe_event` tests assert on `.text` and are rewritten to assert on
`render_row(Locale::En, &row.msg)` — same expectations, one indirection. No behavior changes for a
reader on `en`.

## 7. Testing

All host-side unless noted: `cd ui-dioxus && cargo test --features desktop`.

**Catalog integrity**
- *(compile-time, not a test)* A missing key or a missing locale for a key fails to compile — §1.
- `catalog_has_no_empty_strings`: for every `Msg::ALL` × `Locale::ALL`, `t()` is non-empty and not
  whitespace-only. Catches the stub the compiler cannot.
- `placeholder_sets_match_across_locales`: for every `Msg`, the set of `{name}` placeholders in each
  locale's template equals `en`'s. This is the invariant `tf` depends on (§1).
- `no_unmatched_braces_in_catalog`: every template's braces are balanced `{name}` pairs.

**Locale resolution**
- `from_tag` normalization: `en_US`/`EN-us`/`  en  ` → `En`; `pt-BR` → `None`.
- Chinese script handling: `zh-Hans`/`zh-CN`/`zh` → `ZhHans`; `zh-Hant`/`zh-TW` → `None`.
- `resolve_locale` precedence — the AC's named test: a persisted `de` beats env `["es"]` → `De`.
- Persisted-garbage fallthrough: persisted `xx-YY` with env `["es"]` → `Es`.
- Env ordering: `["fr", "de"]` → `De` (first *parseable*, not first).
- Empty everything → `En`.

**View model**
- `render_row` per `RowMsg` variant on `en`, replacing the current `describe_event` text assertions.
- `render_row` on a non-`en` locale for one variant of each shape (plain, parameterized, boolean),
  asserting the row differs from `en` — proves rows actually retranslate.
- Server-originated passthrough: a `Log { message }` and a `Verify { detail }` render their payload
  byte-identically in `en` and `zh-Hans` (the §2 boundary, asserted).
- `capability_segments` / `status_label` localize: labels and values differ between `en` and `de`,
  and the segment count and `degraded` flags are locale-invariant.

**Existing tests that must keep passing unchanged**
- `editor/dirty.rs`'s `render_tests` mount the real `Editor` with **no** context provider
  (`dirty.rs:111-123`). They must still pass **without modification** — that is the assertion that
  `use_locale()`'s `try_consume_context` fallback (§5) actually works. If they need editing to
  survive, the fallback was implemented wrong.
- A new test mounts `StatusLine` provider-less and asserts it renders `en` rather than panicking,
  making the fallback explicit rather than incidental.

**Persistence**
- The desktop path round-trips through a `tempfile` config dir (`store` → `load`), and `load`
  returns `None` for an absent file and for garbage contents.
- The web path is not host-testable; it is covered by the wasm build check and manual smoke (§10).

**Build checks**
- `cd ui-dioxus && cargo build --target wasm32-unknown-unknown --features web` — the AC.
- `cd ui-dioxus && cargo build --no-default-features` — the neither-feature configuration still
  compiles (both persistence and detection must degrade cleanly).
- `cd ui-dioxus && ./scripts/build-web.sh` — the four bundle-trust guards, including
  `MAX_WASM_BYTES`. Five catalogs are expected to cost single-digit KB; if this guard fires, the
  mechanism choice in §1 was wrong and must be revisited rather than the ceiling raised.
- The browser integration tests (`--target wasm32-unknown-unknown --features web`) still pass. They
  assert on the `connect_probe` transport recorder, not on visible text
  (`web_mount_test.rs:165-225`), so they are expected to be unaffected — verified, not assumed.

## 8. Error handling & edge cases

| Case | Behavior |
|---|---|
| Unmatched/partially-matched browser locale (`fr`, `pt-BR`, `zh-Hant`) | Falls back to `En`. Never a partial catalog — there is no such thing here, since every key exists in every locale by construction. |
| `localStorage` unavailable or throwing | Swallowed; detection-only. No error row, no console noise. |
| Config dir unresolvable or unwritable (desktop) | Swallowed; detection-only. |
| Persisted tag no longer valid (a locale removed in a future build) | Treated as absent → detection applies. |
| `navigator.languages` empty or absent | Falls through to `navigator.language`, then to `En`. |
| A `tf` arg missing for a template placeholder | Renders the literal `{name}` — visible, reportable, not silent. |
| A path or server message containing `{` or `}` | Single-pass substitution never rescans values; renders verbatim. |
| Locale switched mid-turn | Purely a view re-render. The socket, session, `last_seq`, editor buffer, dirty flag, and pending approval are untouched (§5). |
| Locale switched with a pending approval open | The panel's copy retranslates; the pending `(id, path, old, new)` tuple is untouched, so the verdict still correlates. |
| RTL | None of the five locales is RTL. Out of scope, and the layout is not prepared for it. |
| Desktop folder-picker title shows a stale locale | **Known, accepted.** `desktop_boot::boot()` is a free async function outside the component tree, so it has no hook access and resolves its title through `initial_locale()` rather than the live signal. If a user changed language and then triggered a new pick within the same session, the dialog title would lag. In practice `boot()` runs once at launch, before the UI mounts, so the window is effectively nil — but it is a real asymmetry with every other string in the app, and it is recorded rather than left for someone to rediscover. |
| Very long translated button text (e.g. German) | A pre-existing CSS concern, not an i18n one. `style.css` is checked for fixed-width button rules during implementation; if any exist, they are relaxed — otherwise no CSS change. |

**Pluralization** is not needed: no message counts a noun. `seq {n}`, `↑{in} ↓{out} tok`, and
`(+{n} bytes)` are all unit-suffixed rather than pluralized, and stay that way. If a future message
needs plurals, the catalog gains a second entry point rather than the runtime gaining a rules
engine.

**Number and currency formatting** is explicitly out of scope. The cost meter's `${cost:.4}` keeps
its `en-US`-shaped decimal point and leading `$` in every locale. Doing this properly needs
locale-aware grouping/decimal separators and a currency the engine does not report — an ICU-scale
dependency that would dwarf the entire catalog. Recorded as a known limitation (§11), not silently
skipped.

## 11. Risks & open questions

1. **Translation quality.** The catalogs are authored without a native reviewer for de/es/hi/zh-Hans.
   Terms of art (`sandbox`, `token`, `seq`, `Promote`/`Demote`) are the likely weak points. Mitigation:
   keep the untranslated protocol identifiers untranslated (§2) so a mistranslation can never make a
   user's report unmappable, and treat the catalogs as revisable copy — a later PR fixing wording
   touches one file and no logic. **This is the largest known risk in the change and is accepted
   deliberately**, because five imperfect catalogs plus a correct mechanism is strictly better than
   no localization, and the mechanism is the part that is expensive to change later.
2. **Bundle growth — MEASURED, and the original estimate was wrong.** This spec predicted
   "single-digit KB." The real figure, measured by `./scripts/build-web.sh` on the finished
   branch, is **834,754 B against the 795,188 B baseline — ~39.5 KB of growth**, roughly 4–5× the
   estimate. All four guards pass with ~365 KB of headroom, so the ceiling was never at risk and
   §1's mechanism choice stands.

   The estimate was wrong because it counted only the catalog's *string data*. The other
   contributors, none of them accounted for: the macro-generated match arms (5 arms × 47 keys),
   the `RowMsg`/`render_row` dispatch added by the §6 log refactor, the `LanguagePicker`
   component, and the wasm-bindgen glue pulled in by four new `web-sys` features
   (`Navigator`/`Storage`/`Document`/`Element`).

   Recorded as a correction rather than quietly left, because the next person to reason about
   this crate's budget should start from 834,754 B and a real decomposition — not from a
   prediction that turned out to be off by 4×.
3. **`sys-locale` and `dirs` are new desktop-only dependencies.** Both are small and neither can
   reach the wasm build (optional, under `desktop`). `dirs` is already a workspace dependency at
   `crates/engine/Cargo.toml:37`, pinned `5` — but `ui-dioxus/` is its own workspace root with its
   own lockfile, which that pin does not constrain. It ships **`6`**, deliberately: this crate's
   lockfile already resolves `dirs 6.0.0` transitively via `wry`/`tray-icon`, so pinning `5` "for
   consistency" would add a SECOND `dirs` tree (5.0.1 + dirs-sys 0.4 + option-ext) rather than
   reuse the one already linked. Matching the workspace number would have cost dependencies, not
   saved them.
4. **The `LogRow` refactor is the widest blast radius in this change** — it touches `view_model.rs`,
   `event_log.rs`, and every push site in `app.rs`. It is mechanical and fully covered by the
   rewritten row tests, but it is where a mistake would land.
5. **Number/currency formatting stays `en`-shaped** (§8). A German reader sees `$0.0042`, not
   `0,0042 $`. Known and accepted.
6. **`zh` bare → Simplified** (§3) is a judgment call for a tag considered alone, mitigated by the
   picker. It is *not* what a Traditional environment resolves to: `resolve_locale`'s scan is
   variant-aware and suppresses a bare `zh` that follows an already-rejected `zh-*`, so
   `["zh-TW", "zh", "en"]` → `En`. See §3 — the rule only holds composed, not per-tag.
7. **Open:** whether the desktop config file should be JSON rather than a bare tag, in anticipation
   of a second preference. Deliberately deferred — §4 argues the second preference is the right
   moment to decide the file's shape, and a one-line tag file is trivially migratable.

## 12. Assumptions

Every choice made without asking, with its rationale.

1. **The issue's inventory is a starting point, not a closed set.** Three files it omits carry
   user-facing copy (premise 1); they are in scope because the AC is "no user-facing string literal
   remains," which is a property of the tree, not of the list.
2. **A hand-rolled catalog is preferred over a library.** §1 — the bundle guard and the wasm
   dual-target constraint make dependency-free the cheapest correct answer at this catalog size.
3. **Capability values are UI copy, not diagnostics** (§2) — the strip exists to make lost
   capability legible.
4. **Server-originated text is out of scope** (§2). The issue calls this out as needing an explicit
   decision; it is technically impossible client-side, so the decision is forced, and the *framing*
   around it is translated instead.
5. **`Role` and event-kind names stay untranslated** (§2) — shared vocabulary with the engine, the
   docs, and any bug report.
6. **The picker lives in `StatusLine`** (§5) — always rendered, chrome not workflow.
7. **The log must retranslate live** (§6), which is why `LogRow` changes shape. A mixed-language log
   after a switch would read as a bug.
8. **Persistence is two functions, not a settings layer** (§4) — the issue explicitly asks for it to
   be deliberately small.
9. **The persisted choice is written only on explicit picker use** (§4), so detection never becomes
   accidentally sticky.
10. **`zh-Hant` falls back to `en` rather than to Simplified** (§3) — an honest fallback beats a
    wrong script.
11. **`sys-locale` over env-var parsing** (§3) — env vars are absent on the desktop target's primary
    launch path on two of three platforms.
12. **Number/currency and pluralization are out** (§8) — neither is needed by any current message,
    and doing them properly is an ICU-scale dependency.
13. **The URL placeholder is not copy** (§2) — a diverging-from-the-issue call, recorded as such.
14. **No CSS work is assumed necessary**; `style.css` is inspected for fixed-width text containers
    during implementation and relaxed only if longer translations actually overflow.
15. **The translate boundary is actionable-copy-vs-diagnostic, not authored-vs-received** (§2).
    This is the spec's least obvious call: it excludes six strings this crate genuinely authored,
    on the grounds that they share a surface with permanently-English engine diagnostics and their
    audience is a bug report. The named upgrade path is recorded in §2 so the decision is
    reversible rather than forgotten.
16. **Locale is read through a `use_locale()` helper with a `try_consume_context` fallback, never
    plain `use_context`** (§5) — otherwise the existing provider-less `Editor` render tests panic,
    and every future component test inherits the same trap.

## 13. Goal & success criteria

Give `ui-dioxus/` a dependency-free, compile-time-verified localization layer covering every string
this crate authors, in five languages, with environment detection, an accessible in-UI picker that
switches language live without touching the session, and a persisted choice on both targets — while
keeping the wasm bundle under its existing guard and leaving every workspace crate untouched.

- No **UI-copy** literal remains outside `src/i18n/` — verified by reading the diff of every file in
  §2's first table. The exclusions in §2's second table (server-originated payloads, protocol
  identifiers, crate-authored technical diagnostics, the URL placeholder, glyphs, structural
  strings) are enumerated exhaustively there, so "was one missed?" stays checkable rather than
  a matter of taste.
- All five catalogs are complete by construction (compile error otherwise), non-empty and
  placeholder-consistent by test.
- `resolve_locale` precedence (persisted > environment > `en`) and `zh`/`zh-Hant` handling are
  unit-tested on the host — including the **composed** browser/POSIX list shapes
  (`["zh-TW", "zh", "en-US", "en"]`, `["zh-Hant-HK", "zh", "en"]`, `zh_TW:zh:en`), not only
  `from_tag` in isolation, which is where a Traditional environment would otherwise slip through
  to Simplified.
- Switching locale retranslates the whole UI *including already-received log rows*, with no reload,
  no reconnect, and no change to session, `seq`, editor buffer, or pending approval.
- The choice survives a restart on both targets, and beats detection on the next startup.
- `cargo build --target wasm32-unknown-unknown --features web`, `cargo build --no-default-features`,
  `cargo test --features desktop`, the browser integration tests, and `./scripts/build-web.sh` (all
  four guards) pass.
